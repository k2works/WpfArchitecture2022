# ビジネスユースケース - AdventureWorks 購買管理システム

## 概要

本ドキュメントは、AdventureWorks 購買管理システムのビジネスユースケースを詳細化したものです。要件定義書で特定されたビジネスユースケースを完全形式で記述します。

## BUC001: 再発注要求確認🖥️🌊

**使用時のコンテキスト**: 在庫レベルが閾値を下回った際に、購買担当者が要再発注製品を確認し、適切な発注計画を立てる

**スコープ**: AdventureWorks 購買管理システム

**レベル**: ユーザー目的

**主アクター**: 購買担当者

**利害関係者と利益**:

- 購買担当者: 効率的に要再発注製品を特定し、在庫切れリスクを回避したい
- 在庫管理担当者: 在庫状況が適切に購買部門に伝達されることを確認したい
- 購買マネージャー: 購買計画が適切に立てられ、コスト最適化が図られることを期待

**事前条件**:

- 在庫管理システムが稼働している
- 各製品に適切な在庫閾値が設定されている
- ベンダー情報が最新の状態で維持されている

**最低保証**: 要再発注製品の一覧が正確に表示される

**成功保証時**: 購買担当者が要再発注製品を適切に確認し、次の発注処理に進める状態となる

**トリガー**: 在庫管理システムから在庫閾値を下回った製品の通知を受信

**主成功シナリオ**:

1. システムが在庫管理システムから要再発注製品情報を取得する
2. 購買担当者が要再発注製品一覧画面を表示する
3. システムが製品ごとに以下の情報を表示する：
   - 製品情報（名前、カテゴリ、サブカテゴリ）
   - ベンダー情報
   - 推奨発注数量
   - 単価と小計
   - リードタイム情報
   - 現在在庫数量
4. 購買担当者が製品一覧を確認し、発注対象製品を選択する
5. システムがベンダーごとに製品をグループ化して表示する
6. 購買担当者が発注計画を確定する

**拡張**:

- 3a. 要再発注製品が存在しない場合: システムがメッセージを表示し、定期チェック画面に戻る
- 4a. 製品の詳細情報が必要な場合: 製品マスタ画面に遷移して詳細を確認
- 5a. ベンダー情報に問題がある場合: ベンダー管理画面に遷移して情報を更新

**技術およびデータのバリエーションリスト**:

- 3a. データ取得方法: リアルタイム取得 / バッチ取得
- 5a. グループ化条件: ベンダー別 / 製品カテゴリ別 / 納期別

**関連情報**:

- 在庫管理システムとのデータ連携仕様
- ベンダー情報管理規則
- 発注数量計算ルール

## BUC002: 発注処理🖥️🌊

**使用時のコンテキスト**: 購買担当者が要再発注製品を確認後、ベンダーに対して正式な発注を作成・送信する

**スコープ**: AdventureWorks 購買管理システム

**レベル**: ユーザー目的

**主アクター**: 購買担当者

**利害関係者と利益**:

- 購買担当者: 効率的かつ正確に発注書を作成し、ベンダーに送信したい
- ベンダー: 正確で完全な発注情報を適切なタイミングで受信したい
- 購買マネージャー: 発注内容と金額が適切であることを確認したい

**事前条件**:

- 要再発注製品が確認済みである
- 発注対象のベンダー情報が有効である
- 発注権限を持つユーザーがログイン済みである

**最低保証**: 発注情報が正確に記録される

**成功保証時**: 発注書がベンダーに送信され、発注記録がシステムに保存される

**トリガー**: 購買担当者が要再発注製品確認後に発注処理を開始

**主成功シナリオ**:

1. 購買担当者が発注作成画面を表示する
2. システムが選択された製品情報をプリセットする
3. 購買担当者が発注詳細を入力・確認する：
   - 発注数量
   - 納期希望
   - 配送方法
   - 特記事項
4. システムが発注金額を自動計算する（小計、税額、送料、総額）
5. システムが発注内容の妥当性をチェックする
6. 購買担当者が発注内容を最終確認する
7. システムが発注書を生成する
8. システムがベンダーに発注書を送信する
9. システムが発注記録を保存する
10. 購買担当者に発注完了通知を表示する

**拡張**:

- 5a. 妥当性チェックエラーの場合: エラー内容を表示し、修正を促す
- 8a. ベンダーへの送信が失敗した場合: エラーログを記録し、手動送信オプションを提示
- 9a. 発注記録の保存が失敗した場合: システム管理者に通知し、手動での対応を依頼

**技術およびデータのバリエーションリスト**:

- 8a. 送信方法: 電子メール / EDI / Web API / FAX
- 4a. 金額計算: 標準税率 / 製品別税率 / 地域別税率
- 7a. 発注書フォーマット: PDF / Excel / CSV / XML

**関連情報**:

- ベンダー別送信方法設定
- 発注書テンプレート仕様
- 発注金額計算ルール
- 発注権限マトリックス

## BUC003: 発注承認🖥️🌊

**使用時のコンテキスト**: 購買マネージャーが作成済みの発注内容を確認し、承認または差し戻しを行う

**スコープ**: AdventureWorks 購買管理システム

**レベル**: ユーザー目的

**主アクター**: 購買マネージャー

**利害関係者と利益**:

- 購買マネージャー: 発注内容が適切であることを確認し、承認プロセスを効率的に実行したい
- 購買担当者: 承認結果を迅速に受け取り、必要に応じて修正対応を行いたい
- 経営陣: 購買統制が適切に機能していることを確認したい

**事前条件**:

- 発注が作成済みで承認待ち状態である
- 購買マネージャーがシステムにログイン済みである
- 承認権限が適切に設定されている

**最低保証**: 承認結果が正確に記録される

**成功保証時**: 発注が承認され、ベンダーへの正式送信が可能な状態となる

**トリガー**: 購買担当者による発注作成の完了通知

**主成功シナリオ**:

1. 購買マネージャーが承認待ち発注一覧を表示する
2. システムが承認が必要な発注を表示する
3. 購買マネージャーが対象発注を選択する
4. システムが発注詳細情報を表示する：
   - 発注概要（ベンダー、総額、発注者）
   - 発注明細（製品、数量、単価、小計）
   - 承認基準との照合結果
   - 過去の発注履歴との比較
5. 購買マネージャーが発注内容を確認する
6. システムが承認基準を満たしているかチェックする
7. 購買マネージャーが承認を実行する
8. システムが承認記録を保存する
9. システムが発注者に承認完了通知を送信する
10. システムが発注状態を「承認済み」に更新する

**拡張**:

- 6a. 承認基準を満たしていない場合: 警告メッセージを表示し、特別承認オプションを提示
- 7a. 承認を拒否する場合: 拒否理由を入力し、発注者に差し戻し通知を送信
- 8a. 承認記録の保存が失敗した場合: エラーログを記録し、再試行オプションを提示

**技術およびデータのバリエーションリスト**:

- 6a. 承認基準: 金額閾値 / ベンダー信用度 / 製品カテゴリ
- 9a. 通知方法: システム内通知 / 電子メール / SMS
- 4a. 過去履歴の範囲: 3ヶ月 / 6ヶ月 / 1年

**関連情報**:
- 承認権限マトリックス
- 承認基準設定ルール
- 通知設定仕様

## BUC004: 在庫確認🖥️🌊

**使用時のコンテキスト**: 在庫管理担当者が定期的に在庫レベルを確認し、再発注が必要な製品を特定する

**スコープ**: AdventureWorks 購買管理システム

**レベル**: ユーザー目的

**主アクター**: 在庫管理担当者

**利害関係者と利益**:

- 在庫管理担当者: 在庫状況を正確に把握し、適切なタイミングで再発注要求を作成したい
- 購買担当者: 正確な在庫情報に基づいて発注計画を立てたい
- 経営陣: 過剰在庫と在庫切れの両方を防ぎ、最適な在庫水準を維持したい

**事前条件**:

- 在庫管理システムが稼働している
- 製品マスタに在庫閾値が設定されている
- 在庫データが最新の状態に更新されている

**最低保証**: 現在の在庫状況が正確に表示される

**成功保証時**: 再発注が必要な製品が特定され、購買部門に通知される

**トリガー**: 定期的な在庫確認スケジュールまたは手動での確認実行

**主成功シナリオ**:

1. 在庫管理担当者が在庫状況画面を表示する
2. システムが全製品の在庫情報を取得する
3. システムが各製品の在庫レベルを閾値と比較する
4. システムが在庫状況を分類表示する：
   - 正常在庫（閾値以上）
   - 要注意在庫（閾値の110%～100%）
   - 要再発注（閾値未満）
   - 在庫切れ（ゼロ）
5. 在庫管理担当者が要再発注製品を確認する
6. システムが各製品の詳細情報を表示する：
   - 現在在庫数量
   - 安全在庫量
   - 過去の使用実績
   - 未完了発注数量
7. 在庫管理担当者が再発注要求を作成する
8. システムが購買部門に再発注要求を通知する

**拡張**:

- 3a. 在庫データの取得エラーの場合: エラーメッセージを表示し、手動再試行オプションを提示
- 5a. 緊急在庫切れの場合: 緊急通知を購買部門に送信
- 7a. 再発注要求の作成をスキップする場合: スキップ理由を記録

**技術およびデータのバリエーションリスト**:

- 2a. データ取得頻度: リアルタイム / 1時間毎 / 日次
- 4a. 在庫分類基準: 固定閾値 / 動的閾値 / ABC分析連動
- 8a. 通知方法: システム内通知 / 電子メール / ダッシュボード表示

**関連情報**:

- 在庫閾値設定ルール
- 在庫分類基準
- 緊急通知設定

## BUC005: 入荷処理🖥️🌊

**使用時のコンテキスト**: 在庫管理担当者が発注済み製品の入荷を確認し、在庫を更新する

**スコープ**: AdventureWorks 購買管理システム

**レベル**: ユーザー目的

**主アクター**: 在庫管理担当者

**利害関係者と利益**:

- 在庫管理担当者: 正確かつ迅速に入荷処理を完了し、在庫情報を最新に保ちたい
- 購買担当者: 発注した製品の入荷状況を確認したい
- 経理担当者: 入荷に伴う支払処理を適切に実行したい

**事前条件**:

- 入荷予定の発注が承認済みである
- 物理的な製品が倉庫に到着している
- 入荷検査が完了している

**最低保証**: 入荷記録が正確に保存される

**成功保証時**: 在庫が正確に更新され、発注状態が完了となる

**トリガー**: 物理的な製品の倉庫到着と検査完了

**主成功シナリオ**:

1. 在庫管理担当者が入荷処理画面を表示する
2. システムが入荷予定の発注一覧を表示する
3. 在庫管理担当者が対象発注を選択する
4. システムが発注詳細と入荷予定情報を表示する
5. 在庫管理担当者が実際の入荷内容を入力する：
   - 入荷数量（発注明細ごと）
   - 入荷日
   - 検査結果
   - 品質状態
6. システムが入荷数量の妥当性をチェックする
7. 在庫管理担当者が入荷処理を確定する
8. システムが在庫数量を更新する
9. システムが発注状態を「入荷完了」に更新する
10. システムが関係者に入荷完了通知を送信する

**拡張**:

- 6a. 入荷数量が発注数量と異なる場合: 差異理由を入力し、購買担当者に通知
- 5a. 品質検査で不合格の場合: 不合格品の処理方法を選択（返品/廃棄/保留）
- 8a. 在庫更新エラーの場合: エラーログを記録し、手動修正オプションを提示

**技術およびデータのバリエーションリスト**:

- 5a. 入荷方法: バーコードスキャン / 手動入力 / 一括取込
- 6a. 妥当性チェック: 数量のみ / 数量と金額 / 数量と品質
- 10a. 通知対象: 購買担当者のみ / 関係者全員 / 設定による

**関連情報**:

- 入荷検査基準
- 品質管理ルール
- 在庫更新仕様
